## 1. Purpose, Scope & Traceability Governance

### 1.1 Purpose of the RTM
The **Requirements Traceability Matrix (RTM)** serves as the authoritative, bidirectional traceability ledger connecting the business goals, operating rules, workflow state machine, and governance boundaries established in the **Business Foundation Document (BFD) v1.5.0** (`KCPC-MKT-BFD-001`) with the atomic, testable engineering specifications in the **Business Requirements Specification (BRS) v1.1.0** (`KCPC-MKT-BRS-001`), and providing the forward baseline for the downstream Software Requirements Specification (SRS) v0.3, technical design, ERD / physical data model, API specifications, UI/UX designs, and test verification suites.

$$\text{BFD v1.5.0} \longrightarrow \text{BRS v1.1.0} \longrightarrow \mathbf{\text{RTM v0.4}} \longrightarrow \text{SRS v0.3} \longrightarrow \text{Design / Data / API / UI} \longrightarrow \text{Test Documentation} \longrightarrow \text{Implementation}$$

### 1.2 Document Precedence & Hierarchy
1. **Authoritative Source of Business Truth:** The **Business Foundation Document (BFD)** (`KCPC-MKT-BFD-001` v1.5.0, frozen in R3.4 and unchanged by R3.5) is the Single Source of Truth (SSOT).
2. **Requirements Baseline:** The **Business Requirements Specification (BRS)** (`KCPC-MKT-BRS-001` v1.1.0, frozen in R3.4 and unchanged by R3.5) translates the BFD into atomic, testable, implementation-agnostic requirements.
3. **Traceability Ledger:** This RTM (`KCPC-MKT-RTM-001` v0.4, R3.5 candidate) records and validates the reciprocal relationships across artifacts.
4. **Precedence Hierarchy:** $\text{BFD} > \text{BRS} > \text{RTM} > \text{SRS} > \text{Design / Data / API / UI} > \text{Test Documentation} > \text{Implementation}$.
5. **Discrepancy Rule:** If any conflict or wording ambiguity arises, the higher document in the precedence hierarchy governs. Discrepancies shall never be silently resolved within the RTM; they must be formally logged in the Traceability Exceptions Register and escalated through formal change control.

### 1.3 Critical Source-Fidelity Discipline
- **No Speculative Requirements:** The RTM captures only verified relationships explicitly supported by the authoritative source documents.
- **Strict Reverse Traceability:** In supporting governance matrices (§4.7), formal BRS mappings are established exclusively where the BRS explicitly cites that BFD source item in its Source Traceability clause. Items without explicit BRS citations are marked `No Direct Requirement Mapping` rather than inferring semantic mappings.
- **No Invented Downstream IDs:** SRS requirement IDs are synchronized from validated `KCPC-MKT-SRS-001` v0.3 (`SRS-REQ-001` through `SRS-REQ-093`). Architecture / Design IDs are synchronized from validated `KCPC-MKT-SAD-001` v0.4 (`SAD-DES-001` through `SAD-DES-034`). ERD / Data Dictionary IDs are synchronized from validated `KCPC-MKT-ERD-001` v0.4 (`ERD-TBL-001` through `ERD-TBL-044` and `ERD-VW-001`, or explicit N/A where ERD §25 establishes no persistent data impact). The API Specification (`KCPC-MKT-API-001` v0.4.0, `API-OP-001`..`API-OP-073`) is authored and synchronized into §3.2. The UI/UX Design Specification (`KCPC-MKT-UIUX-001` v0.1) covers the MVP core production flow at low fidelity. Test Case Specifications remain downstream pending (`TBD — Downstream Pending`).
- **Preservation of Invariants:** All established business invariants (e.g., Single Content ID workflow, Planned Outputs, Reel Types, optional Stage 3 Category free-text, predefined Marks model, Editor assignment timing, employee privacy boundaries, immutable audit trails) are preserved exactly as defined.

### 1.4 Traceability Status Value Definitions

| Status Domain | Permitted Value | Operational Definition |
| :--- | :--- | :--- |
| **Upstream Trace Status** | **Complete** | The BRS requirement is fully, unambiguously, and bi-directionally traceable to explicit BFD section(s), Business Rule(s), KPI(s), Success Criteria, or Permission(s). |
| | **Partial** | The requirement is partially traced, with certain sub-clauses or acceptance criteria requiring further upstream baseline clarification. |
| | **Review Required** | A wording ambiguity, potential conflict, or unmapped dependency exists that requires stakeholder resolution. |

| | **Review Required** | Downstream design or implementation deviates from or conflicts with upstream requirement intent. |

## 2. RTM Architecture & Conventions

### 2.1 Two-Level Architecture Model
To maintain maximum clarity, usability, and rigorous governance without creating an unreadable multi-dimensional matrix, the RTM is structured into two complementary levels:
- **Level 1 — Primary Requirement Traceability Matrices:**
  - **Section 3.1 (Upstream Matrix):** Contains exactly one primary row for each of the 86 formal BRS requirements (`BRS-REQ-001` through `BRS-REQ-086`, incl. R3.4 `BRS-REQ-085/086`), capturing requirement metadata, upstream BFD citations, acceptance criteria lists, upstream trace status, downstream status, and traceability remarks.
  - **Section 3.2 (Downstream Matrix):** Dedicated forward engineering ledger providing discrete, separately maintainable columns for SRS Requirements, Architecture/Design, ERD/Data Dictionary, API Specifications, UI/UX Screens, and Test Cases.
- **Level 2 — Supporting Coverage Matrices:** Dedicated domain-specific matrices verifying complete coverage across all 65 Business Rules (incl. R3.4 BR-064/065), 10 Business Objectives, 30 KPIs, 13 Success Criteria, 17 Operational Permissions, 22 Workflow Statuses, and Project Parameters (Assumptions, Constraints, Dependencies, Risks, Out-of-Scope boundaries).

### 2.2 RTM ID & Numbering Convention
Stable sequential identifiers `RTM-001` through `RTM-086` are assigned 1-to-1 to `BRS-REQ-001` through `BRS-REQ-086`. RTM IDs serve as permanent matrix row keys for configuration management and change tracking, while `BRS-REQ-xxx` remains the authoritative requirement identifier.

### 2.3 Placeholder Convention for Downstream Deliverables
To avoid fabricating downstream technical artifacts ahead of formal engineering design, the following controlled placeholders and synchronized states are utilized across all Level 1 downstream fields:
- **SRS Requirement ID(s):** Mapped to validated `SRS-REQ-xxx` from `KCPC-MKT-SRS-001` v0.3 (unchanged by R3.5)
- **Design / Architecture ID(s):** Mapped to validated `SAD-DES-xxx` identifiers from `KCPC-MKT-SAD-001` v0.4
- **ERD / Data Dictionary ID(s):** Mapped to validated `ERD-TBL-xxx` / `ERD-VW-xxx` identifiers from `KCPC-MKT-ERD-001` v0.4, or explicit N/A where ERD §25 establishes no persistent data impact
- **API Specification ID(s):** `KCPC-MKT-API-001` v0.4.0 (`API-OP-001` through `API-OP-073`)
- **UI/UX Specification ID(s):** `KCPC-MKT-UIUX-001` v0.1 (MVP core flow; remaining screens downstream pending)
- **Test Case ID(s):** `TBD — Downstream Pending`
- **Downstream Trace Status:** `API Designed — UI/UX (core) drafted; Test Pending`

## 5. Critical Business Invariants Verification

During RTM baseline construction, the following **10 Core Invariant Domains** were verified for 100% compliance across all requirements:
1. **Content Identity Invariant:** One Approved Idea $\longrightarrow$ Exactly One Content ID (`C-MMYY-NNNN`, monthly sequence reset) $\longrightarrow$ Multiple Planned Outputs $\longrightarrow$ Exactly One Shared State Machine Workflow. Planned Outputs do not possess independent Content IDs or sub-statuses.
2. **Planned Outputs & Reel Type Model:** Controlled Planned Output Types are **Photography**, **Reel**, **Video**. Reel Type (**Very Short**, **Short**, **Long**) is required and attributable exclusively per Reel deliverable, supporting distinct Reel Types under the same Content ID without numeric duration thresholds.
3. **Stage 3 Category Invariant:** Captured during Stage 3 Planning as an optional, manually entered free-text attribute (single field, supporting one or multiple category values as typed by the user, or left blank when undecided; not selected from a reference list and not backed by catalogue reference data), attaching to the overall Content ID, conceptually distinct from SKU ID (generic content enters explicit N/A).
4. **Assignment Governance Invariant:** Multiple Camerapersons and multiple Editors are supported per deliverable. Initial Cameraperson assignment occurs during Stage 3 Planning; initial Editor assignment is strictly deferred to Stage 5 (after Shoot Approval).
5. **Predefined Marks Model:** Predefined role Marks (Cameraperson Mark and Editor Mark) are selected at Idea Approval from controlled list `[0, 0.5, 1.0, 2.0, 3.0]`. Qualifying final contributors confirmed at Shoot/Edit Approval each receive the full predefined role Mark without splitting or averaging. Request Rework and Reposts create zero personal Mark attribution. Predefined Mark corrections require Permission #1 and generate linked immutable audit records.
6. **Review Gate Invariant:** Idea Review is a dedicated evaluation gate. Formal production review gates are Planning Review (`PLRV`), Shoot Review (`SRV`), and Edit Review (`ERV`). Publishing and Performance Tracking contain zero separate review statuses. Employee self-approval is strictly prohibited.
7. **Publishing & Multi-Channel Invariant:** Multiple Actual Publication events may exist under one Content ID (including separate posts on the same target). Publication Event Types are `Original` and `Repost`. Publication events do not create the Cameraperson/Editor personal Mark attribution established through Shoot/Edit Approval; Reposts explicitly create zero additional personal Mark attribution records. Publication Target N/A exception handling is auditable, reversible, and cannot result in an all-N/A completed deliverable.
8. **Performance Tracking & Scorecard Invariant:** Performance is tracked per Actual Publication event. Performance Due Date is automatically calculated as $\text{Actual Publication Date} + 2\text{ calendar days}$ (non-reschedulable). Metrics are captured using the authoritative Creative Performance Scorecard with frozen rate formulas and N/A handling.
9. **Access Control & Privacy Invariant:** Exactly 3 internal access classes (CEO / Owner, Marketing Manager, Employee) — over which the R3.4 expandable Business Role (designation) catalogue is layered, each Business Role resolving to exactly one of these three classes — and exactly 17 CEO-Granted Operational Permissions. All access administration is exclusive to the CEO. Employees view own tasks, own Marks, and own 5-measure performance indicators; peer comparison, rankings, compensation, and leaderboards are strictly prohibited.
10. **State Machine & Operational Admin Governance Invariant:** Exactly 22 formal workflow statuses/flags. Status transitions are 100% system-generated; manual status skipping or editing is prohibited. Administrative actions (Reschedule, Reassign, Cancel, Reopen, Reopen Completed, Hold & Resume BR-063) are operational actions rather than distinct base workflow statuses, generating immutable audit log records while preserving primary state identity.
