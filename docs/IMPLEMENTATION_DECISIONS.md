# Implementation Decisions — KCPC R3.5

Ordinary engineering choices (build-prompt §4) recorded here, not as business rules.

| ID | Decision | Rationale |
|---|---|---|
| ENG-001 | Java 21 language level (`maven.compiler.release`), built/run on installed JDK 26 | Java 21 is the current LTS; Spring Boot 3.3.x targets it. JDK 26 is backward-compatible for `--release 21` compilation. |
| ENG-002 | Spring Boot 3.3.5, `war` packaging, executable via `java -jar` (embedded Tomcat) | JSP rendering under embedded Tomcat requires `war` packaging (Spring Boot docs); still runs as a single executable artifact for Docker, and remains deployable to an external servlet container if ever needed. |
| ENG-003 | Lombok omitted from entities/services so far (plain getters/setters) | Kept explicit for clarity while the domain model was still being worked out; may be introduced later for DTOs/mappers if boilerplate grows. |
| ENG-004 | `base_roles` (3 fixed access classes) modeled as a Java enum (`AccessClass`), not a JPA entity, though the DB table still exists and is FK-referenced by `business_roles` | It's fixed reference data with exactly 3 rows that never change; an enum is simpler and type-safe at the application layer while the DB table/FK/CHECK still enforces the physical contract. |
| ENG-005 | `User.businessRole` is `FetchType.EAGER` (ERD/JPA would default associations to LAZY) | `open-in-view` is disabled (correct practice); the resolved access class is read on nearly every authenticated request via `KcpcUserPrincipal`, built inside `JwtAuthenticationFilter` outside any open Hibernate session. EAGER avoids `LazyInitializationException` without resorting to OSIV. |
| ENG-006 | Timestamps (`created_at`, `updated_at`, event timestamps) populated via Hibernate `@CreationTimestamp`/`@UpdateTimestamp`, not relied upon from the DB `DEFAULT CURRENT_TIMESTAMP` | Hibernate always sends an explicit value in generated INSERT/UPDATE statements, so a DB-side `DEFAULT` never fires unless the column is also marked non-insertable - which would leave the in-memory entity stale after save. Column-level `DEFAULT CURRENT_TIMESTAMP` is kept in the DDL as a defensive fallback (e.g. for any future direct-SQL path) but the application never depends on it. |
| ENG-007 | `PermissionGrant.permission` (`OperationalPermission`) and `PermissionGrantStageScope.stageNumber` (`LifecycleStage`) use custom `AttributeConverter`s keyed on each enum's declared numeric code, not `@Enumerated` | The DB columns are `INTEGER` FKs into fixed lookup tables (`operational_permissions.permission_number`, `permission_grant_stages.stage_number`); `EnumType.ORDINAL` would silently write the wrong integer (Java enum declaration order) and `EnumType.STRING` would violate the column's INTEGER type entirely. |
| ENG-008 | `ip_address` columns (`user_sessions`, `system_audit_log`) mapped via `@JdbcTypeCode(SqlTypes.INET)` rather than `columnDefinition = "inet"` | Postgres's JDBC driver rejects an implicit `varchar -> inet` bind in a prepared statement; Hibernate 6's native `SqlTypes.INET` support binds correctly against the PostgreSQL dialect. |
| ENG-009 | Idea ID (`IDEA-YYYYMMDD-NNNN`) daily sequence derived via `COUNT(business_idea_code LIKE 'IDEA-YYYYMMDD-%') + 1` inside the submission transaction, not a dedicated locked sequence table | Unlike Content ID (`ERD-CON-038` mandates `SELECT ... FOR UPDATE` locking via `content_id_sequences`, `ERD-TBL-042`), the ERD defines no equivalent sequence table for Idea IDs, and the build prompt (§9) prohibits inventing new tables for convenience. At MVP scale (<15 users), the small race-condition window (two truly simultaneous same-day submissions could compute the same NNNN) is an accepted, disclosed risk rather than a schema deviation. |
| ENG-010 | `content_id_sequences` first-of-month row creation guards against an insert race (two concurrent transactions both finding no row for a new month) by catching the unique-constraint violation and re-reading under the row lock | `ERD-CON-038` mandates the FOR-UPDATE lock, but a lock can only be taken on a row that already exists; the very first allocation of a month has no row to lock yet. This closes that narrow window without weakening the locking guarantee for every subsequent allocation that month. |
| ENG-011 | Demo/seed data (`db/migration-demo/`) isolated into its own Flyway location, only added to `spring.flyway.locations` under the `dev` profile | Keeps the production/docker profile's schema exactly the governed physical model plus the one bootstrap CEO account - no demo accounts or sample data ever ship outside local development. |
| ENG-012 | GET `/api/v1/csrf` added as an unauthenticated priming endpoint that reads the request-scoped `CsrfToken` | `CookieCsrfTokenRepository` only writes the CSRF cookie when something actually resolves the deferred token (a JSP evaluating `${_csrf.token}` does this implicitly for browser flows); a pure JSON/REST client that never renders a JSP has no other way to obtain the cookie before its first unsafe request. This is the standard Spring Security pattern for REST/SPA CSRF priming - the token is not treated as a secret to the legitimate client (the cookie is deliberately JS-readable); the double-submit protection comes from same-origin policy, not token secrecy. |

| ENG-013 | "Start Shooting" (SA→SIP) and "Start Editing" (EA→ED), and submitting Shoot/Edit Review, are gated to native CEO/MM authority **or** an actively assigned Cameraperson/Editor on that Content Plan - not a CEO-Granted Operational Permission | The 17-permission catalogue has no permission for "begin work" or "submit for review" (only Assignment #4/#6 and Review #5/#7 exist); gating on active-assignee membership is the natural reading of BFD's SIP/ED status descriptions ("physically underway") and avoids inventing an 18th permission, which build-prompt §7 explicitly prohibits ("Strictly NO Permission #18 exists"). |
| ENG-014 | Shoot/Edit Review "qualifying final contributor(s)" are supplied explicitly by the reviewer as a recipient list at Approve time, validated against the recorded execution-participants snapshot taken at review submission | BRS-REQ-033/037 requires the reviewer to confirm which of the (possibly multiple) assigned contributors qualify as final for Mark attribution; the participants snapshot (`shooting_execution_participants` / `editing_execution_participants`, ERD-TBL-038/039) is both the self-review-conflict source of truth and the eligible-recipient allow-list, so a reviewer cannot attribute a Mark to someone who was never actually on the job. |
| ENG-015 | Planning Review approval performs a double workflow hop (PLRV→PLAP→SA) and Edit Review approval performs a double hop (ERV→EAP→RFP) inside one transaction, each recording two `WorkflowTransitionHistory` rows | BFD's status catalogue describes PLAP and EAP as immediately trigger the next state ("Planning Approved: ...triggers task activation in Shoot Assigned"; "Edit Approved: ...transitions to Ready for Publishing"), i.e. they are momentary pass-through states, not states the system waits in. Both hops are recorded for full audit fidelity rather than skipping the intermediate status. |

| ENG-016 | Scorecard draft/submit is hard-blocked before `performance_due_date` (rejects with `VALIDATION_FAILED`), rather than merely not triggering the PP→PFUP transition | Caught during golden E2E testing: allowing early entry while gating only the *transition* on due-date-reached left completion logic (which requires PFUP) unreachable after an early submission, stranding the deliverable at PP forever. Blocking early entry matches BFD's PFUP description ("Performance Due Date reached ... begins metric entry") read as a precondition, not just a trigger condition. |

| ENG-017 | `sessionManagement` is fully disabled (`AbstractHttpConfigurer::disable`) on both filter chains, rather than left at `SessionCreationPolicy.STATELESS`; the STATELESS-equivalent "no `HttpSession` touched" behaviour is instead configured explicitly via `RequestAttributeSecurityContextRepository` + `NullRequestCache` | **Bug found by the automated test suite, not by manual testing.** With `SessionCreationPolicy.STATELESS` alone, `SessionManagementFilter` still runs on every request; because our own `JwtAuthenticationFilter` sets a fresh `Authentication` per request (there is no login-form-triggered "authentication event" to distinguish first-login from every-subsequent-request), Spring Security's default `SessionAuthenticationStrategy` composite - which always includes `CsrfAuthenticationStrategy` whenever CSRF is enabled - treated *every single authenticated request* as a new login and rotated/deleted the CSRF cookie server-side in response. `GET /api/v1/auth/me` right after login would silently invalidate the CSRF token primed moments earlier, so the very next POST (e.g. logout) failed CSRF validation with 403. Manual `curl` scripts throughout this build never revealed this because each one re-read the cookie jar file fresh immediately before every POST; `TestApiClient` (and any real fetch/SPA client, or a JSP page reusing one primed token across multiple AJAX calls) holds the token in memory and reuses it, which is exactly the pattern the priming endpoint (`GET /api/v1/csrf`, ENG-012) exists to support. Setting `.sessionAuthenticationStrategy(new NullAuthenticatedSessionStrategy())` on `SessionManagementConfigurer` was tried first and did *not* work (`CsrfAuthenticationStrategy` is still independently appended); fully disabling `sessionManagement` was the fix that actually removes `SessionManagementFilter`, and therefore the trigger point, from the chain. Disabling it also silently reverts to the default `HttpSessionRequestCache`, which calls `request.getSession(true)` on every 401 to stash a `SavedRequest` - so `NullRequestCache` had to be added alongside it to avoid a new, equally unwanted `JSESSIONID` cookie. |
| ENG-018 | `V12__correction_ledgers.sql` adds a single reusable `trg_reject_update_delete()` trigger function attached to all 15 previously-unprotected append-only tables named in `ERD-CON-058` (plus the 3 new correction ledgers), rather than 15 bespoke trigger functions | Same guard logic (`RAISE EXCEPTION` on any `UPDATE`/`DELETE`) applies uniformly; a `DO $$ ... FOREACH ... $$` block attaches it table-by-table. `work_hold_records` is deliberately excluded - its "exactly one Resume transition" semantics are not simple append-only and need a dedicated trigger (tracked under DB-001). |
| ENG-019 | `AdminActionService.reopenCompleted`'s `PUBLISHING_REOPEN` target was corrected from `WorkflowStatus.RFP` to `WorkflowStatus.PUBG`, and the two spec-named endpoints `POST .../reopen-publishing` / `POST .../reopen-performance` (`API-OP-052`/`053`) were added alongside the existing generic `POST .../reopen` | Found while implementing `CORR-001`: `API_Specification.md` §17.8 states the workflow effect as `COMP -> PUBG` for `API-OP-052`, but the shipped code (predating this pass, Phase 9-11) transitioned to `RFP` instead - a genuine defect, not a spec ambiguity, so the code was fixed per this document's Continuous Conformance rule ("If the current code contradicts R3.5: fix the code"). The generic `/reopen` endpoint was kept (nothing depends on removing it) so no existing caller breaks. |
| ENG-020 | Path convention: the 3 new correction endpoints (`API-OP-033/041/046`) were implemented at the exact frozen paths (`/api/v1/ideas/{ideaId}/predefined-marks/corrections`, `/api/v1/publishing/events/{eventId}/evidence-corrections`, `/api/v1/performance/scorecards/{scorecardId}/corrections`); the two new reopen endpoints were added under the pre-existing `content-plans/{id}/...` convention rather than the spec's literal `workflows/{workflowInstanceId}/...` base | See `DISC-001` in `docs/IMPLEMENTATION_DISCREPANCIES.md` - the entire pre-existing Domain 8 (Hold/Resume/Reschedule/Reassign/Cancel/Reopen, Phase 9-11) already uses a `content-plans`-nested convention system-wide, undocumented until this pass. Renaming all of Domain 8 mid-way through `CORR-001` was judged higher-risk than valuable (breaks nothing today, but a wholesale REST surface rename affects every existing admin-action caller/test); recorded as a discrepancy instead of silently changing more of the contract than necessary. The 3 brand-new correction endpoints had no existing convention to conflict with, so they follow the frozen spec exactly. |
| ENG-021 | `V13`'s privilege-GRANT block (Part B) is existence/self-grant-guarded (`IF EXISTS (... kcpc_app ...) AND to_regrole('kcpc_app') IS DISTINCT FROM to_regrole(current_user)`) rather than assuming `kcpc_app` always exists as a distinct role | Local dev/test (`kcpc_dev`/`kcpc_test`) predates this session with a single `kcpc_app` role that is both the Flyway-connecting migrator and the (superuser) runtime role; the guard makes `V13` safely idempotent/no-op there instead of failing or granting a role privileges on itself, while still running for real in docker/prod where `db/init/01_create_app_role.sh` creates a genuinely separate `kcpc_app`. |
| ENG-022 | `db/init/01_create_app_role.sh` creates the restricted `kcpc_app` role via a shell script (`psql` heredoc) rather than a plain `.sql` file under `docker-entrypoint-initdb.d/` | Plain `.sql` init scripts have no environment-variable substitution; the role's password must come from `APP_DB_PASSWORD` (a Docker secret/env var), not be hardcoded into a committed file. A `.sh` script that shells out to `psql` with the variable already in its environment is the standard pattern for parameterized Postgres bootstrap. |
| ENG-024 | `ContentPlan.idea` and `WorkflowTransitionHistory.triggeredBy` changed from `FetchType.LAZY` to `EAGER` | Found by actually running the new MVC screens (§9.2/§9.15) against a live server, not just compiling: `pipeline.jsp` (`plan.idea.title`) and `deliverable-detail.jsp`'s timeline (`t.triggeredBy.fullName`) read these associations directly in the view, outside any open Hibernate session (`open-in-view` is deliberately disabled, ENG-005's precedent), throwing `LazyInitializationException`. Same fix pattern as `ENG-005` - narrow, targeted EAGER on the specific associations actually dereferenced in a view, not blanket OSIV. |
| ENG-023 | `V13` splits `work_hold_records`' DELETE-rejection (new dedicated trigger) from its UPDATE-lifecycle enforcement (existing `trg_work_hold_records_lifecycle` from V9) instead of one combined trigger | V9's trigger already correctly enforces the nuanced "exactly one Resume transition, then fully immutable" UPDATE rule (`ERD-CON-062` rules 6-8) and predates this pass; DELETE was simply never blocked (rule 9 was missed). Adding a second, narrowly-scoped `BEFORE DELETE` trigger closes the gap without touching or risking regression in the already-correct, already-tested UPDATE logic. |
| ENG-026 | New `MasterCatalogueService` + `MasterCatalogueRestController` (Platform/Channel/Target create/update/deactivate, Permission #17) implemented while building the `/app/admin/catalogue` MVC screen (UI/UX v0.2 §6.3), rather than deferred further | `API-OP-036`/`066`..`070` and the entire Permission #17 (`PERM_17_PLATFORM_CATALOGUE_MANAGE`) authorization check were entirely unimplemented (pre-existing gap, not introduced by this pass) - only read-only repository lookups existed internally, with no REST surface and no MVC surface. Since the governed UI screen requires these writes to function at all, closing the backend gap was a prerequisite for the screen, not optional scope creep. |
| ENG-027 | All 30 governed KPIs (`API-OP-058`) implemented via native SQL (`EntityManager.createNativeQuery`) rather than JPQL | JPQL cannot express Postgres date-diff/`EXTRACT(EPOCH FROM ...)` arithmetic or the stage-context `CASE` expression (`STAGE_PLANNED_DATE_CASE`, BR-039: each active deliverable's delay baseline is its *current* stage's planned date - Shoot/Edit/Live - not one fixed column) needed for the duration KPIs (021/025/027/028) and distribution KPIs (006/015/016/029). Non-obvious judgment calls, each grounded in the closest BFD wording: KPI-008/009 default to the current IST calendar month (BFD explicitly says "over monthly periods") when no `startDate`/`endDate` is given, KPI-010/011/022/023 default to all-time; KPI-013/014 "produced **and approved**" is read as "the output's parent plan passed Planning Review" (reached `SA` or later) since that is the concrete governed approval gate outputs pass through; KPI-021's turnaround is `decided_at - submitted_at` on every `review_cycles` row; KPI-027's is `first_completed_at - content_plans.created_at` (Planning starts when the Content Plan is created at Idea Approval); KPI-028's is the first `SAP` transition to the latest `ORIGINAL` publication event per Content ID; KPI-030 scopes "applicable" events to `ORIGINAL` only (a `REPOST` is not a first delivery, matching KPI-012's same `ORIGINAL`-only definition of "published"). |
| ENG-028 | `AdminReportingService.delayedDeliverables`'s Employee read-scope check treats **any** currently-valid `GLOBAL`-scope permission grant as full department-wide visibility, without evaluating `STAGE_RESTRICTED`/`ITEM_SPECIFIC` scope against each individual delayed row | `SRS-REQ-002` requires an Employee's view to include "deliverables falling within the scope of any active CEO-granted operational permission that authorizes acting on this resource." A fully faithful implementation would re-run the same per-item `scopeCovers` evaluation `AuthorizationService` already does for write actions, against every delayed deliverable, for every one of the employee's grants, on every report request - expensive and not yet built for a read-only reporting endpoint. `GLOBAL` scope is evaluated exactly (correct, no gap); `STAGE_RESTRICTED`/`ITEM_SPECIFIC` grant-holders currently see only their own assigned/participated deliverables on this report (an under-not-over-exposure gap - conservative, never leaks peer data, but may hide some in-scope items a narrowly-scoped delegate should see). Tracked as a known limitation, not silently ignored. |
| ENG-029 | `User.getPasswordHash()` marked `@JsonIgnore`; `AuditRestController` returns a new `AuditLogResponse` projection instead of the raw `SystemAuditLog` entity | **Security defect found and fixed while building the Audit Log endpoint (`API-OP-061`), not by manual review.** `SystemAuditLog.actor` is an EAGER `User` association (necessary for MVC/JSP rendering per ENG-005/ENG-024's pattern); returning the entity graph directly from a REST controller serialized the actor's bcrypt password hash straight into the JSON response. Every other controller in the codebase already avoided this by construction (`UserProfileResponse`, `AuditLogResponse`, etc. instead of raw `User`) - this was the first place a `User`-bearing entity graph was returned unprojected. `@JsonIgnore` on the getter is added as defense-in-depth so the same mistake anywhere else in the API surface fails safe instead of leaking; `ReportingApiSecurityTest` asserts no bcrypt-shaped string ever appears in a response body. |
| ENG-030 | `MultiFormatExportService` (`API-OP-062`) uses a fixed `Set<String> GOVERNED_TABLES` allowlist, validated *before* any value is interpolated into a `SELECT * FROM <table>` native SQL string, and reads generically via `JdbcTemplate.queryForList` (column-name-keyed maps) rather than per-table JPA entity/DTO mappings; XLSX and the full export payload are built fully in memory rather than true chunked/streamed generation | The allowlist is a hard SQL-injection guard - `tables` is caller-supplied and must never reach string concatenation unchecked. Generic `SELECT *` + column-map rows avoids hand-writing ~31 per-table export DTOs for a feature whose whole purpose is a raw physical-table dump (the ERD, not a curated API shape, *is* the contract here per RTM-081). In-memory buffering is an accepted simplification at the `SAD-ADR-009`/`010`-declared &lt;15-concurrent-user MVP scale; the response is still a single synchronous stream to the client as `SRS-REQ-080/081` require, just not internally chunked during generation. |
| ENG-031 | `KpiValue`, `AuditLogResponse`, and `DelayedDeliverableRow` implemented as plain classes with explicit `getX()` accessors, not Java `record`s, even though every other read-only DTO added this session (e.g. `MultiFormatExportService.ExportResult`) is a record | **Bug found by actually running the new report screens against a live server, not by compiling or unit-testing.** `/app/reports/kpis` and `/app/audit` both returned a misleading `302` redirect to `/login?reason=auth` - looking exactly like an authentication failure - when in fact classic JSP EL's `BeanELResolver` (used by `<c:forEach>`/`${...}` in these JSPs) only recognizes `getX()`-prefixed JavaBean accessors, not a `record`'s no-prefix canonical accessors (`displayValue()`, `eventTimestamp()`); the resulting uncaught `jakarta.el.PropertyNotFoundException` was caught by the security filter chain's exception handling and re-surfaced as an auth redirect, masking the real cause. Fixed by converting all three JSP-rendered DTOs to plain classes and updating every record-accessor call site (`k.code()` → `k.getCode()`, etc.) in `KpiService`/`ReportingMvcController`. `ExportResult` stays a record because it is never rendered by a JSP - only read in Java (`ExportRestController`). Rule going forward: any DTO dereferenced directly inside a JSP must be a plain class with `getX()` methods, never a record. |
| ENG-032 | `JwtAuthenticationFilter.shouldNotFilterErrorDispatch()` overridden to return `false` (re-run the filter on the container's internal `/error` forward, not just the original request); the dead `/app/admin/permissions` nav link in `pipeline.jsp` removed (permission administration is a read-through from `/app/admin/users/{id}`, per UI/UX v0.2 §6.2 - it was never a standalone screen) | **Real, user-reported bug: "clicking the Permissions tab logs me out."** Root cause was systemic, not specific to that one link: `OncePerRequestFilter` skips itself by default on Spring Boot's internal forward to `/error` (triggered by any unmapped URL's 404 or any uncaught exception's 500). With the filter skipped, no authentication is populated for that forwarded dispatch, `anyRequest().authenticated()` fails, and `MvcAuthEntryPoint` redirects to `/login?reason=auth` - indistinguishable from a real logout, and masking the true 404/500 status entirely (this is the same underlying mechanism that made the `ENG-031` bug's symptom look like an auth failure rather than a rendering exception). Verified live: before the fix, `curl`-ing an authenticated session against any unmapped `/app/**` path returned `302` to `/login`; after the fix, the same request correctly returns `404` and the session remains valid for a real screen immediately after. Regression-guarded by `AuthenticationFlowTest.unmappedAppUrlReturnsA404NotALoginRedirectWhileAuthenticated`. The immediate trigger (the dead nav link) was a genuine second bug layered on top - `/app/admin/permissions` was never wired to any `@GetMapping`, so it always 404'd, which the auth-dispatch bug then disguised as a logout. |
| ENG-033 | New `/app/admin/permissions` screen: a CEO-exclusive, read-only, all-users consolidated list of every currently active `PermissionGrant` (`PermissionGrantAdminService.listActiveGrants`, new `PermissionGrantSummary` plain-class DTO, `PermissionGrantRepository.findByActiveTrueOrderByEffectiveFromDesc`) | User request, after the dead `/app/admin/permissions` link (`ENG-032`) was removed: "can we keep a list of who currently has what permission, in one place" - the existing §6.2 read-through (open a user, see their grants) already answered "what does this one user have," but not "who across the whole org currently holds permission #N." Not a new governed screen in the frozen UI/UX spec (it extends the existing §6.2 read-through into an all-users view rather than introducing new business rules, fields, or a new permission), so implemented as a small additive read-only extension rather than a contract change - no new REST endpoint, no write path, same CEO-exclusive authority check (`requireCeo`) as every other permission-administration action. Grant/revoke *history* (not just current state) was already available via the Audit-History screen (`PERMISSION_GRANTED`/`MODIFIED`/`REVOKED` events, `ENG-029`'s reporting work) and needed no new work. `PermissionGrantSummary` follows the `ENG-031` plain-class-not-record rule since it is rendered directly by a JSP; grantee/grantor names and stage-scope labels are all resolved eagerly inside the service's `@Transactional` method, since `PermissionGrant.grantee`/`grantor` are LAZY associations that would otherwise throw `LazyInitializationException` when read from the JSP outside the session (`ENG-005`/`ENG-024` pattern). Regression-guarded by an assertion added to `AdminMvcScreenSmokeTest`. |
| ENG-034 | New `HighPriorityEdgeCaseTest` (5 tests) closing the specific gaps identified when asked "have you tested all scenarios": multi-contributor Mark attribution (two qualifying Camerapersons/Editors each get the FULL predefined Mark, never split), an expired delegated permission grant (403 `PERM_OPERATIONAL_PERMISSION_EXPIRED`), a revoked delegated permission grant, and a `STAGE_RESTRICTED` grant used outside its covered stage (403 `PERM_OPERATIONAL_PERMISSION_OUT_OF_SCOPE`) | A genuine, non-obvious finding while writing the revoked-grant test: `AuthorizationService.requireAuthority` fetches candidate grants via `findByGranteeAndPermissionAndActiveTrue` - a *revoked* grant (`active=false`) is therefore invisible to that query entirely, so it is correctly classified as `PERM_OPERATIONAL_PERMISSION_REQUIRED` ("never granted"), not `PERM_OPERATIONAL_PERMISSION_EXPIRED` - a distinct code path from a grant that is still fetched but whose `effective_until` has lapsed. Confirmed correct (not a defect) by first proving the same grant works before revocation, then asserting the exact post-revocation error code, so the test cannot silently pass for the wrong reason. All 5 scenarios passed against the real implementation with no code changes required elsewhere. |
